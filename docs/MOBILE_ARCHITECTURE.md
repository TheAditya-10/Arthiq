# Mobile Architecture

## 1. Framework Choice

React Native + TypeScript, bootstrapped via **Expo prebuild (bare workflow)** rather than Expo Go / Expo-managed-only. Rationale (ADR-005): the app needs a custom native Android module (`NotificationListenerService` in Kotlin) that cannot run inside Expo Go's sandboxed runtime. `expo prebuild` generates the native `android/` project once, which then owns the custom module, while everything else (navigation, UI, networking, most device APIs) still uses the Expo SDK and its JS-first developer experience. This means:
- `npx expo run:android` for local development (builds + installs via Gradle, no EAS account required).
- `npx expo prebuild` regenerates `android/` from `app.json`/plugins when config changes — the custom native module is wired in via a **local Expo Config Plugin** (`apps/mobile/plugins/withNotificationListener.ts`) so `android/` stays regeneratable rather than hand-edited-and-fragile.
- No EAS Build/Submit dependency — all builds are local Gradle builds, per the requirement to build APK/AAB locally.

## 2. App Structure

```
apps/mobile/
├── app.json                       Expo config (+ plugin registration)
├── plugins/
│   └── withNotificationListener.ts  Config plugin: adds the Kotlin service +
│                                     manifest entries + permission to android/
├── android/                        Generated by `expo prebuild` (native Kotlin module lives here,
│                                    persisted because it's hand-written, not regenerated)
│   └── app/src/main/java/.../notifications/
│       ├── ArthiqNotificationListenerService.kt
│       ├── NotificationParsers.kt      (Kotlin mirror used only for pre-filtering by package;
│                                        the actual parsing logic lives in TS — see §3)
│       └── NotificationListenerModule.kt (Expo Modules API bridge: exposes
│                                        start/stop/getAccessStatus/openSettings to JS,
│                                        and emits an event with the raw
│                                        {packageName, title, text, postTime} to JS)
├── src/
│   ├── app/                        screens: Home, Transactions, People, Add, Settings
│   ├── navigation/
│   ├── api/                        typed fetch client (mirrors apps/web's, sharing
│   │                                packages/types + packages/validation)
│   ├── notifications/
│   │   ├── providers/               GooglePayParser.ts, PhonePeParser.ts, PaytmParser.ts,
│   │   │                            GenericUPIParser.ts — same shape as documented in
│   │   │                            docs/CLASSIFICATION_ENGINE.md's sibling doc,
│   │   │                            RECONCILIATION_ENGINE.md's dedup section
│   │   ├── dedupCache.ts            local recent-hash ring buffer (AsyncStorage-backed)
│   │   └── syncQueue.ts             queues ingest POSTs, retries with backoff when offline
│   ├── auth/                        secure token storage (expo-secure-store), refresh flow
│   └── state/                       lightweight client state (React Query for server state;
│                                     no heavy global state library needed)
└── __tests__/                       parser unit tests (recorded sample notification strings)
```

**Why parsing logic lives in TypeScript, not Kotlin**: the native Kotlin module's only job is to (a) register as a `NotificationListenerService`, (b) filter by package name against the enabled-provider allow-list (cheap, avoids bridging irrelevant notifications to JS at all), and (c) bridge the raw `{packageName, title, text, postTime}` to JS via an Expo Modules API event. All actual text parsing happens in TypeScript (`src/notifications/providers/*`), so the parser logic is: written once, unit-testable with Vitest/Jest without an emulator, and shared in spirit (same pattern, same test fixtures) with anything the backend might ever need to re-parse from `NotificationSource.rawText` in a debug scenario.

## 3. Notification Flow (device-side)

```
StatusBarNotification posted
        │
        ▼
ArthiqNotificationListenerService.onNotificationPosted (Kotlin)
        │  filter: is packageName in enabled-provider allow-list? (from JS-synced settings,
        │  persisted natively so filtering works even before JS/RN has initialized)
        ▼  (if allowed) emit event to JS via NotificationListenerModule
        │
        ▼
JS: providers/index.ts picks the parser for packageName → parse(title, text, postTime)
        │  null result → dropped, nothing stored/sent
        ▼ (ParsedTransaction)
dedupCache.ts: hash check against recent local cache (handles OS re-posting same notif)
        │  duplicate → dropped
        ▼
syncQueue.ts: enqueue POST /notifications/ingest (JWT attached); retried with backoff if
        offline; queue persisted to AsyncStorage so app kill/restart doesn't lose it
        ▼
On success: local push notification shown:
   "₹480 at Zomato — Food → Delivery  [Correct] [Change]"
   (bucket/sub-bucket/confidence come back in the ingest response)
```

## 4. Permissions

- `android.permission.INTERNET` — sync to backend.
- Notification access is **not** a manifest `<uses-permission>` alone — it requires the user to enable the app under Settings → Notifications → "Notification access" (a special access grant, Android's `BIND_NOTIFICATION_LISTENER_SERVICE`). The app cannot request this via a runtime permission dialog; it can only deep-link the user there via `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`, exposed to JS as `NotificationListenerModule.openSettings()`. Documented step-by-step in `docs/ANDROID_SETUP.md`.
- `POST_NOTIFICATIONS` (Android 13+ runtime permission) — needed for the app's own local "Correct/Change" notifications, requested normally via Expo's notifications API.

## 5. Settings Screen (Privacy Control, per spec §22)

`src/app/Settings` lets the user toggle each provider (`Google Pay`, `PhonePe`, `Paytm`, `Generic UPI`) independently. Disabled providers are filtered out **natively** (the Kotlin allow-list check) so a disabled provider's notifications never even reach JS — not just ignored after the fact. Settings persist locally (AsyncStorage) and mirror to `PATCH /notifications/settings` for auditability, but the on-device allow-list is authoritative for what gets processed on that device.

## 6. Background Reliability

`NotificationListenerService` is a bound system service, not a typical background task — Android keeps it alive as long as notification access is granted and the OS itself isn't aggressively killing the process (see `docs/MOTOROLA_SETUP.md` for OEM-specific battery-optimization exemptions this depends on in practice). No `WorkManager`/foreground-service polling hack is used to "keep it alive" — that would be fighting the platform rather than using its documented mechanism correctly. The mitigation for OEM kills is user-facing guidance (Motorola setup doc) plus the architectural stance that notification ingestion is best-effort (ADR-005) with CSV import as the reconciliation backstop.

## 7. Navigation (per spec §27)

People       — people ledger list + person detail + record lending/repayment
