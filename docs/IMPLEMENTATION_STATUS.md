## Phase 16 — Deployment

- **Status**: Complete
- **Completed work**: This phase found and fixed one real, latent bug and several stale-documentation issues rather than writing new application code — deployment work is mostly "does the packaging actually work," which turns out to matter.
  - **`apps/api/Dockerfile`'s runtime stage had a real bug**: it copied `apps/api/node_modules` and the workspace root `node_modules` directly into the final image. pnpm's default `node-linker` is `isolated` (symlinks into a shared content-addressable store at `node_modules/.pnpm`), so those `node_modules` entries are symlinks with relative paths computed against the _build_ directory structure — copying them into a differently-shaped runtime image (`/app` instead of `/repo/apps/api`) would have produced dangling symlinks, i.e. `Cannot find module` at container startup. Never caught before because the container path has never actually been run — Vercel serverless (Option A) was always the path actually exercised in this project's own development. Fixed by switching the runtime stage to `pnpm --filter @arthiq/api deploy --prod /out` — pnpm's own documented mechanism for producing a self-contained, non-symlinked directory for exactly this use case — and copying every workspace member's `package.json` (not just `@arthiq/api`'s) into the `deps` stage, since pnpm's `--filter` install needs to see the full workspace manifest set to resolve correctly rather than falling back to over-fetching.
  - **Verified the Vercel serverless adapter actually works**, without needing a real Vercel account: wrote a local smoke script that imports `apps/api/src/adapters/vercel.ts`'s exported `handler` directly, wires it to a plain Node `http.Server`, and hits it with real requests — `GET /health` (200, correct body) and a full `POST /auth/register` (201, real Postgres write, real JWT issuance, real cookie handling) both worked correctly through the exact handler function Vercel would invoke. This is the meaningful part of ADR-007's adapter pattern (one Vercel-aware file, wrapping the same `buildApp()` everything else uses) and it holds up.
  - **`docs/DEPLOYMENT.md` had drifted from reality**: the Vercel adapter's documented path (`apps/api/adapters/vercel.ts`) was missing the `src/` segment; `CORS_ALLOWED_ORIGIN` (singular) doesn't match the actual env var (`CORS_ALLOWED_ORIGINS`, comma-separated, plural); and it listed `JWT_REFRESH_SECRET` as required. That last one is actually a phantom — refresh tokens in this system are opaque random bytes hashed with SHA-256 (`apps/api/src/lib/refreshToken.ts`), never JWTs, so there has never been a `JWT_REFRESH_SECRET` to set; grepping the whole codebase for `process.env.` confirms nothing reads it. Removed it from both `docs/DEPLOYMENT.md` and `.env.example` rather than leave a var that looks required but does nothing. Also added `LOG_LEVEL` to `.env.example` (a real, used, previously-undocumented optional var — `apps/api/src/app.ts` reads it with an `"info"` default).
  - **`apps/web`'s Vercel path was already correct as documented** (no code changes needed) — it's a standard Next.js app; `next build` has been passing since Phase 1 and the only per-environment configuration is `NEXT_PUBLIC_API_URL`, already documented.
- **Verification performed**: `docker build --check` (BuildKit's structural linter — parses and validates the Dockerfile, including stage references and syntax, without running it) passes clean on the corrected Dockerfile. The two local adapter smoke tests above both passed against the real dev database. Full workspace `pnpm lint`, `pnpm typecheck`, `pnpm build`, and `pnpm test` all still pass (133 tests, no regressions from this phase's changes — none of them touched application logic).
- **Known limitation, stated plainly**: An actual end-to-end `docker build .` was attempted twice and did not complete in this sandbox — not a bug in the new Dockerfile, but the same network-flakiness constraint against `registry.npmjs.org` documented since Phase 10's mobile dependency install crisis (a `pnpm install --frozen-lockfile` inside a fresh, empty Docker build context has no access to this host's already-populated pnpm store, so it re-fetches the full resolved lockfile graph from the registry — corroborated by both attempts' progress logs showing hundreds of packages, including ones unrelated to `@arthiq/api`, being fetched directly from npm rather than reused). The `pnpm deploy`-based fix is correctness-reasoned and lint-verified, not full-build-verified — that distinction is being stated plainly rather than glossed over, consistent with this project's standing practice for every other sandbox limitation. Actually deploying either app to a live Vercel project was not attempted at all — that requires the user's own Vercel account and is exactly the kind of "creating/modifying a real external resource" action this assistant does not take without the user directly doing it themselves; `docs/DEPLOYMENT.md` documents the steps for the user to run.
